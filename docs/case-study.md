# 三分钟讲清一笔申请

这里介绍一笔申请在平台中的完整分析路线。正式原始记录、完整逐项特征和用户保存资料不随仓库分发；下面仅保留必要的示例输出和聚合结果。

## 1. 从业务目标开始（约 30 秒）

“项目用公开匿名申请和申请前历史，预测来源定义的还款困难事件。它是研究和本机演示工具，没有固定期限 PD 或实际审批的主张。”

## 2. 解释资料怎样成为输入（约 45 秒）

“一笔申请可以对应多条历史记录。先检查父子键和相对时间，再分别汇总历史，最后关联回一笔申请一行。完整输入是 71 项，不能随意填几个页面字段就代替模型的完整资料。”

可以当场运行[虚构 SQL 示例](../examples/sql_walkthrough.py)，手算 2×2 明细连接为什么重复计算，说明有效 0 与 null 的区别。这比只浏览页面更能说明分析思路。

## 3. 展示结果并讲清阈值（约 45 秒）

本机保存的示例申请 100006，在当前 71 项模型下预测约 **25.14%**，高于 **7.65%** 分析阈值。它属于 validation，不能用它演示正确就声称泛化已通过。

“这是模型估计，并不表示已经证明此人的真实违约概率为 25.14%。阈值由研究验证集选择，误报率约 36.60%，所以标记结果只能作为研究复查线索。”

## 4. 从解释回到证据（约 35 秒）

本机工作台可查看主要因素、完整输入、历史来源、资料缺口和训练参考。说明因素来自模型响应；“已关闭”不自动推断已结清，“住宅／公寓”不推断产权，金额不擅自写人民币或月薪。部分月度来源在界面中是保存汇总，不能声称全量原始流水均已展示。

## 5. 保存与复核（约 25 秒）

资料保存、重开、分析、模拟复核和固定报告构成工程闭环，报告绑定申请与模型版本。本仓库提供相应代码阅读入口；完整运行需要本机未分发的可信资产。

固定报告保存当次分析快照，后续资料修改不自动改写旧报告。查看报告时应核对申请、输入修订、模型与阈值是否一致，避免把不同版本结论混用。
